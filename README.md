# workspace

2026 年秋季《软件工程课程设计》项目仓库。

## 项目章程

### 背景与目标

本项目面向需要同时管理个人事务与团队协作的小组，建设轻量级协作办公平台。拟以校园项目小组为首批用户，通过真人访谈确认现有资料共享、会议安排和权限管理中的问题，并以访谈纪要和试用反馈作为需求依据。

### 范围与角色

- **个人工作区**支持资料上传、分类、查看、下载和个人日程管理。个人资源仅本人可访问。
- **共享工作区**支持成员邀请、角色管理、共享资料及共享日程。所有者管理成员和共享内容，编辑者维护共享内容，查看者只读。
- **外部集成**采用第三方登录，优先验证目标部署环境中的登录流程。通知提醒、全局搜索和日历订阅根据试用反馈与进度安排。

### 交付与验收

计划以三轮迭代交付三个可部署、可演示的增量，每轮有计划、构造、测试、评审和回顾。具体日期由小组结合课设安排确定。

| 增量 | 交付范围 | 核心验收场景 |
|---|---|---|
| **v0.1 个人工作区** | 第三方登录、个人资料、个人日程 | 用户登录后上传、分类和下载资料，并创建、查看个人日程。 |
| **v0.2 共享资料与成员权限** | 创建共享工作区、邀请成员、分配角色、共享资料 | 所有者邀请成员，编辑者上传资料，查看者可下载资料，其修改请求被拒绝。 |
| **v0.3 共享日程** | 创建、查看和修改共享日程，处理并发编辑冲突 | 编辑者修改会议后，查看者可看到更新。两个编辑者提交冲突修改时，系统保留先保存的内容，提示另一人重新加载后提交。 |


### 风险与项目治理

- **技术风险**是资源归属或成员状态判断错误，导致跨工作区访问。架构与测试角色共同跟踪风险，在首轮验证私有资源隔离，在第二轮将跨工作区访问、角色限制和成员移除后的访问结果纳入回归测试。共享日程的并发修改另设非功能验收用例。
- **需求和验收**由组员确认。需求变更通过 Issue 申请、评审、批准并留痕，批准后更新需求基线及相关设计和测试。设计规约正式评审，验收用例由客户视角成员编写。

## 过程模型选型论证

采用**用例驱动的增量迭代**。增量决定每版交付什么，迭代评审决定怎样根据反馈调整，关键用例贯通需求、设计和测试。

| 候选模型或方法 | 适用场景 | 本项目的取舍 |
|---|---|---|
| **增量模型** | 业务可以分成逐步扩展且独立可验收的版本 | 作为主模型。个人工作区可先独立使用，共享资料建立成员关系与权限，共享日程在其基础上扩展。三版均交付完整业务流程。 |
| **螺旋模型** | 关键技术或外部依赖的不确定性较高，试验结果会决定下一轮工作 | 借鉴风险驱动。资源归属与访问权限会影响资料和日程，首轮先验证访问边界，再按业务增量推进。 |
| **UP（统一过程）** | 用例之间存在依赖，需要早期验证架构，并在需求、设计和测试之间建立追溯关系 | 借鉴用例驱动和架构先行。先明确资源归属与权限规则，再用同一用例编号关联需求、设计、Issue 和测试，按课程要求裁剪工作产品。 |
| **敏捷（借鉴 Scrum）** | 项目有持续反馈来源，功能优先级需要随着试用调整 | 采用短迭代、评审和回顾。根据试用反馈调整共享日程细节和扩展功能优先级，已确认需求的变更纳入 Issue 评审。 |

每轮先明确本版用例和验收标准，再构造、测试和评审，发布时更新追溯关系并记录回顾。规格先行用于约束 AI 辅助工作。架构决策、需求确认和合并放行由组员把关，AI 辅助产出须经过人工检查并记录用途。

延伸讨论见[过程模型选型论证](docs/01-charter/过程模型选型论证.md)，版本计划以本章程的交付表为准。

## 仓库结构

```
docs/          课程交付物，按 8 个知识单元编号组织（见 docs/README.md）
src/           应用源码
tests/         单元测试与集成测试
scripts/       仓库卫生检查等工具
.github/       CI、PR/Issue 模板
.githooks/     本地提交前检查
```

## 快速开始

```bash
git clone https://github.com/beigu-8-lyw/workspace.git
cd workspace
cp .env.example .env          # 填入本地配置，.env 不会入库
git config core.hooksPath .githooks && chmod +x .githooks/pre-commit
python3 scripts/check_repo.py  # 仓库卫生自检
```
